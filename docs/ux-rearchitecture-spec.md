# CursorDance UX 重构规格 v1

状态：信息架构与交互原则已定稿，下一阶段进入「应用规则」低保真原型。

## 1. 目标

本轮重构不以增加功能为目标，而是让已有能力围绕用户任务重新组织。

核心目标：

1. 用户能分清「当前主题设置」与「全局设置」。
2. 所有页面使用一致的标题、主操作、编辑、保存与反馈模型。
3. 普通用户不需要理解进程名、Glob、热点坐标等实现概念，也能完成核心任务。
4. 高级能力保留，但延后到用户明确需要时再展示。
5. 平台能力不同的页面允许采用不同任务流，不为了代码复用强求同构 UI。

本轮非目标：

- 不修改 schema v4 的持久化格式。
- 不改变应用规则「第一条命中规则生效」的运行时语义。
- 不新增规则类型、时间计划或云同步。
- 不先建设一套抽象页面组件再套业务页面。
- 不进行官网或品牌视觉重做。

## 2. 产品作用域

界面必须明确表达以下作用域，不能再依赖用户从数据行为中猜测。

| 功能 | 作用域 | 当前存储位置 | 页面要求 |
| --- | --- | --- | --- |
| 动作与效果 | 当前主题 | `themes[].actionConfigs` | 显示「正在编辑：主题名」 |
| 光标皮肤 | 当前主题 | `themes[].cursorSkin` | 显示「正在编辑：主题名」 |
| 键盘反馈 | 当前主题 | `themes[].keyFeedbackConfig` | 显示「正在编辑：主题名」 |
| 站点规则 | 全局 | `contextRules[context=web]` | 隐藏主题侧栏，显示「全局设置」 |
| 应用规则 | 全局 | `contextRules[context=desktop]` | 隐藏主题侧栏，显示「全局设置」 |
| 全局启用 | 全局即时控制 | `enabled` | 独立于草稿保存，明确反馈结果 |
| 诊断 | 全局只读工具 | 运行时状态 | 不显示主题保存操作 |

规则可以引用主题，但规则本身不属于某个主题。删除被规则引用的主题时，确认界面必须列出受影响的站点/应用规则数量；确认删除后，在同一个配置草稿事务中把这些规则降级为「跟随全局主题」（`action: { type: "enable" }`）。不能留下悬空引用，也不能静默删除规则。若删除的是运行中的当前主题，同时把运行主题切换到确认界面展示的后备主题。

## 3. 导航信息架构

一级导航按用户意图分组，而不是按现有组件平铺：

### 个性化

- 主题与效果
- 光标皮肤
- 键盘反馈

### 自动化

- Chrome 扩展：站点规则
- Electron 桌面端：应用规则

### 系统

- 诊断与性能

AI 助手保持为「主题与效果」中的协作侧栏，不作为一级工作区。

导航约束：

- 主题侧栏只在「个性化」分组中显示。
- 进入「自动化」或「系统」时，主内容获得完整页面宽度。
- 当前作用域固定出现在页面标题区域，不随滚动消失。
- 桌面端和扩展端可以使用相同分组，但只展示平台真实支持的入口。

## 4. 保存与状态模型

### 4.1 四类状态

界面必须区分：

1. **导航状态**：工作区、当前主题、动作、光标状态。自动保存，不产生配置未保存提示。
2. **即时运行控制**：全局启用。操作后立即持久化，并显示「已启用」或「已暂停」。不进入草稿。
3. **配置草稿**：主题、光标、键盘、站点与应用规则的改动。进入统一未保存事务。
4. **局部编辑草稿**：正在填写但尚未完成的一条规则。只存在于当前编辑器，不立即写入配置草稿。

### 4.2 用户可见行为

- 规则编辑器的提交按钮命名为「完成」，不能使用「保存」。
- 「完成」只把局部编辑内容写入配置草稿。
- 页面固定保存栏统一提供「保存更改」与「放弃更改」。
- 离开存在未完成局部编辑的页面时，提示「继续编辑 / 放弃本条编辑」。
- 离开存在配置草稿的页面时允许切换工作区，但关闭窗口或切换主题时必须明确提示。
- 保存成功后显示简短状态，不同时叠加 Toast、按钮变化和多处文案。

### 4.3 内部状态建议

持久化仍使用一份原子 schema v4 配置，但编辑器内部将当前单一的 `ui.unsaved` 拆为：

```ts
type DirtyState = {
  global: boolean;
  themes: Record<string, boolean>;
};
```

- 应用/站点规则变更设置 `global=true`。
- 主题、光标皮肤、键盘反馈变更设置对应 `themes[themeId]=true`。
- 一次「保存更改」仍可原子写入全部配置。
- 保存栏根据当前页面显示「当前页面有更改」；如果其他作用域也有改动，显示「另有 N 处更改」。
- 全局启用不设置 DirtyState。

新主题不应在用户不知情的情况下部分自动保存。创建完成后进入配置草稿，并由统一保存栏提交。

### 4.4 现有行为迁移约束

- 主题导航选择只写编辑器状态，不能再隐式改写 `activeThemeId` 或制造配置未保存状态；改变运行主题必须使用独立、明确的「设为当前主题」操作。
- 全局启用的即时持久化只能基于最后一次已保存配置更新根字段 `enabled`，不能从当前工作台状态重建整份配置，否则会顺带提交主题或规则草稿。
- 全局启用写入失败时，开关回滚到最后一次已保存值，并在开关附近提供单一错误反馈与重试入口；已有配置草稿保持不变。
- 移除现有「主题数量增加即自动写入整份配置」的副作用。新建、复制和导入主题都只进入主题草稿；关闭窗口时沿用未保存更改保护。
- 上述调整只改变编辑器事务边界，不改变 schema v4，也不需要迁移用户已有配置。

## 5. 统一页面骨架

每个一级页面按同一骨架组织：

1. `PageHeader`
   - 标题
   - 一句话说明
   - 作用域标签
   - 页面级状态
   - 唯一主操作
2. `PageBody`
   - 列表、画布或编辑器主任务
   - 不重复页面标题
3. `Inspector`（按需）
   - 当前对象的详情和高级设置
   - 不承担页面主操作
4. `SaveBar`（有配置草稿时出现）
   - 改动摘要
   - 放弃更改
   - 保存更改

页面约束：

- 一个页面只能有一个视觉上的主操作。
- 普通流程不使用 `text-2xs` 承载必要信息。
- hover 不能是编辑、删除或排序的唯一入口。
- 空状态首先提供下一步，不先解释内部模型。
- 删除、重置、清空全部必须提供确认或可撤销反馈。
- 权限错误、数据为空、当前未命中、保存失败是不同状态，不混用同一警告卡。

## 6. 应用规则产品模型

### 6.1 用户语言

应用规则默认以以下句式呈现：

> 在「Visual Studio Code」中，使用「流光」主题。

> 在「Keynote」中，关闭 CursorDance。

进程名、窗口标题、精确匹配、通配符和优先级属于高级条件，不是默认创建流程的必填概念。

### 6.2 核心任务

P0：

1. 为刚才使用的应用关闭效果。
2. 为刚才使用的应用指定主题。
3. 修改已有应用的行为。
4. 暂停、恢复、删除一条规则。
5. 理解刚才使用的应用实际命中了哪条规则。

P1：

1. 按窗口标题创建高级规则。
2. 使用通配符匹配一组窗口。
3. 调整规则优先级并理解覆盖关系。

### 6.3 默认创建流程

第一步：选择应用。

- 默认突出「使用刚才的应用」。
- 显示应用名称、图标（可获得时）和最近窗口标题。
- 次级入口为最近检测到的应用。
- 手动填写进程名放在「找不到应用？」中。

第二步：选择行为。

- 关闭效果。
- 跟随全局设置。
- 使用指定主题。

第三步：确认。

- 用自然语言总结规则。
- 主按钮为「完成」。
- 「高级条件」折叠入口保留匹配目标和匹配方式。

默认流程生成现有 schema 能表达的规则：

```ts
{
  match: { target: "process", type: "exact", value: processName },
  action: { type: "disable" } | { type: "enable", themeId?: string }
}
```

因此低保真原型不依赖 schema 迁移。

### 6.4 应用数据来源与降级

- 桌面主进程现有前台窗口监控每 250ms 读取一次快照，并在 CursorDance 工作台置前时保留最后一个非 CursorDance 快照。因此界面称其为「刚才使用的应用」，不误称为正在前台的「当前应用」。
- 快照当前稳定提供 `owner.name`、`processName`、窗口标题和可选 `bundleId`。基础流程以 `owner.name` 作为应用显示名，以 `processName + exact` 生成规则。
- 「最近使用」列表由渲染进程在本次工作台会话内收集授权后的快照、去重并保留最近 8 个；它属于临时选择数据，不写入 schema v4。应用优先用 `bundleId` 去重，无 `bundleId` 时退回标准化后的 `processName`。
- 现有快照不提供应用图标，低保真不能依赖图标完成识别。无图标时显示统一应用占位图形和应用名称；后续即使补充原生图标 IPC，也不改变选择流程。
- 权限状态直接使用 `authorized`。用户从系统设置返回后，事件流自动重新检测，同时保留显式「重新检测」操作。
- 无法取得快照但并非权限问题时，显示独立的检测失败状态，并保留「手动填写」入口，不能冒充空状态。

### 6.5 页面状态

低保真必须覆盖以下状态：

1. **权限未授予**
   - 解释为什么需要权限。
   - 主操作「打开系统设置」。
   - 次操作「重新检测」。
   - 不展示无意义的空规则编辑器。
2. **无规则**
   - 显示刚才使用的应用卡片。
   - 主操作「为这个应用添加规则」。
   - 次操作「选择其他应用」。
3. **有规则**
   - 每条规则以应用为主体，而不是匹配表达式为主体。
   - 显示应用、行为、主题、启用状态和当前命中状态。
4. **创建/编辑**
   - 使用右侧抽屉或固定 Inspector，不把表单插入列表顶部。
   - 关闭抽屉时处理未完成局部编辑。
5. **规则冲突**
   - 第一条命中规则显示「当前生效」。
   - 后续同样命中的规则显示「被第 N 条覆盖」。
   - 提供上移/下移；拖拽只是增强方式。
6. **保存失败**
   - 保留草稿。
   - 明确重试入口。

### 6.6 规则列表信息层级

一级信息：

- 应用名称和图标。
- 行为：关闭 / 跟随全局 / 使用主题。
- 是否当前生效。

二级信息：

- 规则是否启用。
- 主题名称。
- 优先级。

高级信息：

- 进程名。
- 窗口标题条件。
- exact / glob。
- 原始匹配值。

编辑、启停、删除必须常驻或进入明确的更多菜单，不能只在 hover 时出现。

## 7. 光标皮肤后续约束

本规格不进入光标皮肤原型，但先固定边界，避免应用规则重构时继续强化错误的页面骨架。

- 光标皮肤属于当前主题。
- 桌面端按两个可达状态设计，扩展端按六个可达状态设计。
- 默认任务是「上传普通光标并立即预览」。
- 拖拽状态默认继承普通状态。
- 热点坐标、批量导入、原图信息属于高级设置。
- 状态导航只能保留一套。
- 预览必须模拟真实交互场景，不能把普通导航命名为「试用区」。

## 8. 实现边界

可以继续复用：

- `ContextRuleV4` 和现有匹配器。
- 前台应用快照与授权状态。
- 规则命中测试和第一条命中语义。
- 主题选择数据源。
- 底层 Button、Select、Dialog 等 UI 原语。

不应继续让代码复用决定交互：

- 应用规则和站点规则不再共享完整列表/编辑器布局。
- `RulePrimitives` 仅保留无业务语义的字段、动作选择和匹配辅助能力。
- 应用选择器、应用卡片、权限状态和当前命中摘要由应用规则模块独立实现。

## 9. 验收指标

应用规则重构完成后：

- 新用户在 30 秒内为刚才使用的应用创建禁用规则。
- 默认流程中不出现「进程名」「窗口标题」「通配符」等术语。
- 用户能在列表中直接判断刚才使用的应用实际生效的行为。
- 所有功能可在不使用拖拽和 hover 的情况下完成。
- 用户不会把规则编辑器的「完成」误认为已经持久化。
- 权限、空状态、匹配、冲突和保存失败均有独立测试。
- 现有 schema v4 配置能够无损读取和保存。

## 10. 低保真原型输入清单

下一阶段需要绘制以下 6 张低保真页面：

1. 权限未授予。
2. 已授权、无规则。
3. 已授权、有规则且当前命中。
4. 选择当前/最近应用。
5. 创建规则基础流程。
6. 展开高级条件与规则冲突。

保存失败作为第 3、5 张页面的状态变体标注，不另增主页面；必须表现为草稿仍保留、错误原因和明确的重试入口。

原型只验证信息架构、任务顺序、反馈和保存模型，不讨论颜色、阴影、插画或最终动效。
